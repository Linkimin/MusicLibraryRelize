# MusicBakh 1.0.3 — Итерация C: рейтинги, лайки, теги-ярлыки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Дать пользователю личные оценки треков (0–5★, лайк/дизлайк) и пользовательские теги-ярлыки (mood/situation: «утро», «работа», «тренировка»), плюс фильтры по ним. Параллельно — техдолг итерации B: починить порядок FTS-выдачи в UI, закрыть автоматическим тестом backfill-сценарий апгрейда `1.0.1 → 1.0.2`, и сделать **первый шаг разгрузки `MainViewModel`** — вынести фильтр-пайплайн в отдельный класс `LibraryFilter`. Это естественный момент: без вынесения `ApplyFilters` после добавления трёх новых критериев фильтрации превратится в спагетти.

**Architecture:** Доменная модель `Track` приобретает поля `Rating` (`int 0..5`, 0 = не оценено) и `Reaction` (enum `None/Liked/Disliked`). Появляется новый агрегат `Tag` (Id, Name, Color?) и связь many-to-many с треком через таблицу `TrackTags`. В `MusicBakh.Core.Abstractions` заводится `ITagRepository`. UI: в карточке трека — компактный 5-звёздочный контрол + 👍/👎-toggle + чипы тегов; в фильтр-панели — слайдер минимального рейтинга, toggle реакции и multi-select тегов. Логика «какие треки показывать» собирается в одном месте — новый `LibraryFilter` в `MusicLibrary.Services.Library` принимает `LibraryFilterCriteria` (search hits, genre, min rating, reaction, tag ids) и возвращает отфильтрованный `IReadOnlyList<Track>`. `MainViewModel.ApplyFilters` становится тонким адаптером: собрать criteria → передать в `LibraryFilter` → положить в `DisplayedTracks`.

**Tech Stack:** .NET 10, EF Core 10 SQLite, без новых NuGet-зависимостей. CommunityToolkit.Mvvm и MediatR-style pipeline — НЕ вводим (ориентир `1.9.0` Architecture hardening).

**Совместимость данных:** существующая БД пользователя обновляется автоматически тремя новыми миграциями:
1. `AddTrackRatingAndReaction` — две колонки `INT NOT NULL DEFAULT 0` + индексы (для будущих query-сценариев).
2. `AddTagsSchema` — таблица `Tags(Id PK, Name UNIQUE, Color NULL)`.
3. `AddTrackTags` — таблица `TrackTags(TrackId, TagId, PRIMARY KEY composite)` с FK на обе и каскадным удалением со стороны `Tracks`.

Существующие FTS-триггеры `Tracks_au` срабатывают на `AFTER UPDATE OF Title, Artist, Album, Genre` — апдейты `Rating`/`Reaction` индекс не дёргают, что нам и нужно (поиск по числовому рейтингу не имеет смысла). Если в будущем понадобится «найти все 5-звёздочные с тегом утро» — это пойдёт через `LibraryFilter`, не через FTS.

**Постусловие итерации:**
- Пользователь может поставить трек 0–5 звёзд, кликнуть лайк/дизлайк, добавить и убрать произвольные теги-ярлыки.
- В фильтр-панели появляются три новых критерия (рейтинг ≥ N, реакция = лайк / дизлайк / любая, теги — multi-select). Все фильтры (включая жанр и поиск) совмещаются через **один** `LibraryFilter`.
- FTS-выдача показывается в порядке `bm25` (а не в порядке `_allTracks`).
- Автоматический тест `Migrate_From_1_0_1_State_Indexes_Existing_Tracks` доказывает, что backfill в `AddTracksFts` находит уже существующие треки.
- `dotnet test --filter "Category!=Benchmark"` зелёный (ориентир: 169 → ~195 тестов).

## Контракты

### `Track` (Core)
```csharp
public sealed class Track
{
    // существующие поля...
    public int Rating { get; init; }                       // 0..5; 0 = «не оценено»
    public TrackReaction Reaction { get; init; }           // None / Liked / Disliked
}

public enum TrackReaction { None = 0, Liked = 1, Disliked = 2 }
```

### `Tag` (Core)
```csharp
public sealed class Tag
{
    public int Id { get; init; }
    public string Name { get; init; } = string.Empty;     // unique, case-insensitive
    public string? Color { get; init; }                    // hex "#RRGGBB", nullable
}
```

### `ITagRepository` (Core)
```csharp
public interface ITagRepository
{
    IReadOnlyList<Tag> GetAll();
    Tag? FindById(int id);
    Tag Add(Tag tag);
    void Update(Tag tag);
    void Remove(int id);

    IReadOnlyList<Tag> GetTagsForTrack(int trackId);
    void AttachTag(int trackId, int tagId);              // idempotent
    void DetachTag(int trackId, int tagId);              // idempotent
}
```

### `LibraryFilterCriteria` + `LibraryFilter` (Presentation)
```csharp
public sealed record LibraryFilterCriteria(
    IReadOnlyList<Track>? SearchHits,    // null = поиск не активен, [] = ничего не найдено
    string? Genre,                        // null = все жанры
    int MinRating,                        // 0 = без ограничения
    TrackReaction? Reaction,              // null = любая реакция
    IReadOnlyCollection<int> TagIds);     // пустой = без фильтра по тегам

public static class LibraryFilter
{
    public static IReadOnlyList<Track> Apply(
        IReadOnlyList<Track> allTracks,
        LibraryFilterCriteria criteria,
        Func<int, IReadOnlyList<int>> tagsOfTrack);   // делегат, чтобы не тащить ITagRepository в pure-функцию
}
```

Ключевая семантика: **порядок результата = порядок `SearchHits`** (если поиск активен) **иначе** = порядок `allTracks`. Это закрывает баг 1.0.2 с потерей `bm25`-релевантности.

## SQL миграции (эскиз)

### `AddTrackRatingAndReaction`
```sql
ALTER TABLE Tracks ADD COLUMN Rating   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE Tracks ADD COLUMN Reaction INTEGER NOT NULL DEFAULT 0;
CREATE INDEX IX_Tracks_Rating   ON Tracks(Rating);
CREATE INDEX IX_Tracks_Reaction ON Tracks(Reaction);
```
**Без обновления FTS-триггеров** — `Rating`/`Reaction` не индексируются в `TracksFts`, и существующий `Tracks_au AFTER UPDATE OF Title,Artist,Album,Genre` их игнорирует ровно как должен.

### `AddTagsSchema`
```sql
CREATE TABLE Tags (
    Id    INTEGER PRIMARY KEY AUTOINCREMENT,
    Name  TEXT NOT NULL,
    Color TEXT NULL
);
CREATE UNIQUE INDEX IX_Tags_Name_NoCase ON Tags(Name COLLATE NOCASE);
```

### `AddTrackTags`
```sql
CREATE TABLE TrackTags (
    TrackId INTEGER NOT NULL,
    TagId   INTEGER NOT NULL,
    PRIMARY KEY (TrackId, TagId),
    FOREIGN KEY (TrackId) REFERENCES Tracks(Id) ON DELETE CASCADE,
    FOREIGN KEY (TagId)   REFERENCES Tags(Id)   ON DELETE CASCADE
);
CREATE INDEX IX_TrackTags_TagId ON TrackTags(TagId);
```
Каскад на стороне `Tracks` — удалили трек, связи ушли. Со стороны `Tags` каскад тоже работает: удалили тег — он автоматически отвязался от всех треков (но удаление seed-trackов запрещено в `SqliteTrackRepository.Remove`, ничего опасного).

### Task 0 — Pre-task: FTS-выдача в порядке `bm25`
Проблема, выявленная в код-ревью итерации B: `MainViewModel.ApplyFilters` теряет порядок `bm25`, потому что после поиска фильтрует `_allTracks.Where(...)` и возвращает их в порядке `_allTracks`. Сервис считает релевантность зря.

- [ ] В `MainViewModel.ApplyFilters` (или сразу в новом `LibraryFilter` из Task 4, если решим объединить) при активном поиске собирать словарь `{trackId → index}` из `_searchService.Search(...)`, фильтровать `_allTracks` по `ContainsKey`, **сортировать `OrderBy(t => order[t.Id])`**.
- [ ] Тест `MainViewModelTests.SearchText_Preserves_SearchService_Order`: stub-`ISearchService` возвращает треки в порядке `[B, A, C]`; в `_allTracks` они лежат как `[A, B, C]`; ожидаем в `DisplayedTracks` → `[B, A, C]`.
- [ ] **Замечание:** если этот фикс делается в Task 4 (внутри `LibraryFilter`), Task 0 сводится только к добавлению теста против текущего MainViewModel — он провалится, и пройдёт после Task 4. Решение по группировке коммитов — на исполнителе.

  ```csharp
  var hits = _searchService is not null && !string.IsNullOrWhiteSpace(SearchText)

      hits,
      SelectedGenre == AllGenres ? null : SelectedGenre,
      MinRating,
      ReactionFilter,
      SelectedTagIds);
  ```

## Сознательные ограничения этой итерации

- **OR-семантика multi-select тегов в фильтре** (не AND). Простое поведение «покажи треки, у которых есть хотя бы один из этих ярлыков». AND можно добавить отдельной кнопкой-переключателем, если по факту использования это окажется нужно.
- **Без drag-and-drop тегов на треки.** Привязка идёт через popup в карточке или через множественное выделение в `TagsWindow` (если решим). DnD — UI-полировка, может прийти в итерации D.
- **Без массовой проставки рейтингов/тегов** через выделение нескольких треков. Тоже UI-полировка, отдельная мини-задача.
- **Без `LibrarySearchQuery` (полная замена `ISearchService.Search`).** Контракт `ISearchService` остаётся узким (`Search(query, limit) → IReadOnlyList<Track>`). Pagination, sort modes, snippets, query diagnostics — это итерации D–E или часть `1.9.0`. Эскиз будущего контракта:
  ```csharp
  public sealed record LibrarySearchQuery(string Text, int Offset, int Limit, SearchSortMode Sort);
  public sealed record SearchResult(IReadOnlyList<Track> Tracks, int TotalCount, IReadOnlyDictionary<int, string> Snippets);
  IReadOnlyList<Track> Search(string query, int limit);              // legacy
  SearchResult Search(LibrarySearchQuery query);                      // future
  ```
- **Полнотекстовый поиск НЕ распространяется на теги.** Поиск работает по `Title/Artist/Album/Genre` как в 1.0.2; ярлыки — отдельный фильтр. Включение тегов в FTS потребует расширения `TracksFts` (новая колонка) и пере-backfill — это потянет отдельную миграцию и слишком много неизвестных для C.

## Технический долг → roadmap разгрузки `MainViewModel`

Код-ревью итерации B зафиксировало рост `MainViewModel`: play logic, search/filter, history, stats window, settings, navigation, hotkeys, deletion, import — всё в одном файле. В этой итерации мы делаем **только первый шаг** — выносим `LibraryFilter` (Task 4). Остальное — отдельный мини-эпик, размазанный по C → H:

| Где | Что выносим | Куда |
|---|---|---|
| **1.0.3 (C, здесь)** | Фильтр-пайплайн | `LibraryFilter` (Presentation.Services.Library) |
| **1.0.4 (D)** | Запись истории прослушиваний и replay | `HistoryRecorder` (вызывается из `MainViewModel` на событиях `IAudioPlayerService`) |
| **1.0.5 (E)** | Управление воспроизведением (play/pause/skip/next/seek/repeat) | `PlaybackController` — оборачивает `IAudioPlayerService` + `IPlaybackQueueStrategy` |
| **1.0.6 (F)** | Удаление трека (UI confirm → файл → cover → repository) | `TrackDeletionUseCase` (`MusicBakh.Application`) |
| **1.0.7 (G)** | Импорт треков (вызов диалога, обработка результата, добавление в библиотеку) | `ImportTrackUseCase` |
| **1.0.8 (H)** | Финальная стабилизация / cleanup | — |
| **1.9.0** | Полный переезд на CommunityToolkit.Mvvm + MediatR-style pipeline | systemic |

Это roadmap, **не контракт**. На каждой итерации D–H будет brainstorming-сессия, и порядок может поменяться, если факты потребуют. Главное — после итерации C `MainViewModel.ApplyFilters` перестаёт быть точкой роста, что снимает основное опасение из ревью 1.0.2.
