# MusicBakh 1.0.2 — Итерация B: FTS5-поиск + расширенная история

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Дать пользователю мгновенный поиск по библиотеке (имя/исполнитель/альбом/жанр) и снять лимит «50 записей» с истории прослушиваний, добавив минимальный экран статистики (Top-50, Recently Played, Never Played). Внутри — FTS5 virtual table со SQL-триггерами синхронизации и тонкая абстракция `ISearchService` / расширение `IListeningHistoryRepository`.

**Architecture:** Поиск живёт за `ISearchService` (`MusicBakh.Core.Abstractions`). Реализация `SqliteFtsSearchService` (`MusicBakh.Infrastructure.Search`) выполняет `MATCH`-запросы к виртуальной таблице `TracksFts` и возвращает уже доменные `Track` (через join к `Tracks` по `rowid`). Никаких новых entity-классов под `TracksFts` не вводим: это «теневая» поисковая таблица, EF её не знает, а синхронизацию делают SQL-триггеры `Tracks` → `TracksFts` (AFTER INSERT/UPDATE/DELETE). Статистика истории добавляется методами в `IListeningHistoryRepository`: репозиторий уже видит весь журнал, остаётся только агрегировать. Презентация получает новые ViewModel'и (`SearchViewModel`, `StatsViewModel`) через DI и встраивается в `MainWindow` без переписывания существующих частей.

**Tech Stack:** .NET 10, EF Core 10 SQLite (`Microsoft.EntityFrameworkCore.Sqlite` — FTS5 включён в собранный нативный SQLite по умолчанию, отдельной зависимости не нужно), xUnit. Без новых NuGet-пакетов.

**Поле Album:** в `Track` появляется опциональное `Album` (string, default ""). Картинка-описание итерации B обещает поиск «по альбому», а доменная модель этого поля сейчас не имеет. Группировка по альбомам и альбомный view — отдельная итерация D, здесь только: поле в модели + чтение из TagLib при импорте + индексация в FTS + новый столбец в SQLite через EF-миграцию `AddTrackAlbum`. UI пока показывает альбом как часть карточки трека опционально (можно вообще не показывать в этой итерации — поле «дозревает» к D).

**Совместимость данных:** существующая БД пользователя обновляется автоматически миграциями EF Core. Две новых миграции:
1. `AddTrackAlbum` — колонка `Tracks.Album TEXT NOT NULL DEFAULT ''` + индекс.
2. `AddTracksFts` — `CREATE VIRTUAL TABLE TracksFts USING fts5(...)`, триггеры, и backfill: `INSERT INTO TracksFts(rowid, ...) SELECT Id, ... FROM Tracks;`.

Откат на 1.0.1 невозможен «по-чистому» (down-миграции не пишем — пользователь не должен откатывать минор-патчи руками), но виртуальная таблица в 1.0.1-коде не используется, поэтому совместимость на чтение сохраняется.

**Постусловие итерации:**
- В `MainWindow` есть поле поиска. Ввод дебаунсится (~250 мс), список треков фильтруется FTS-запросом, фильтр по жанру и поиск работают совместно (AND).
- История больше не обрезается до 50 в БД, только в текущем «недавнем» виджете. Полный журнал доступен через `IListeningHistoryRepository.GetAll(...)`.
- Появилась вкладка/окно «Статистика» с тремя списками: Top-50 за всё время, Recently Played (последние 50 уникальных треков), Never Played.
- `MusicLibrary.Tests` зелёный, добавлено покрытие FTS-репозитория (in-memory или файловая SQLite во временной папке — выбираем по факту, см. Task 9) и агрегаций истории.
- Бенчмарк: поиск по библиотеке из 50 000 треков даёт первые результаты за < 100 мс (требование 1.1.0 DoD из роадмапа).

## SQL: FTS5 миграция (эскиз)

`Up` (raw SQL через `migrationBuilder.Sql(...)`):
```sql
CREATE VIRTUAL TABLE TracksFts USING fts5(
    Title, Artist, Album, Genre,
    content='Tracks', content_rowid='Id',
    tokenize = "unicode61 remove_diacritics 2"
);

INSERT INTO TracksFts(rowid, Title, Artist, Album, Genre)
SELECT Id, Title, Artist, Album, Genre FROM Tracks;

CREATE TRIGGER Tracks_ai AFTER INSERT ON Tracks BEGIN
    INSERT INTO TracksFts(rowid, Title, Artist, Album, Genre)
    VALUES (new.Id, new.Title, new.Artist, new.Album, new.Genre);
END;

CREATE TRIGGER Tracks_ad AFTER DELETE ON Tracks BEGIN
    INSERT INTO TracksFts(TracksFts, rowid, Title, Artist, Album, Genre)
    VALUES ('delete', old.Id, old.Title, old.Artist, old.Album, old.Genre);
END;

CREATE TRIGGER Tracks_au AFTER UPDATE ON Tracks BEGIN
    INSERT INTO TracksFts(TracksFts, rowid, Title, Artist, Album, Genre)
    VALUES ('delete', old.Id, old.Title, old.Artist, old.Album, old.Genre);
    INSERT INTO TracksFts(rowid, Title, Artist, Album, Genre)
    VALUES (new.Id, new.Title, new.Artist, new.Album, new.Genre);
END;
```

`Down` — `DROP TRIGGER`/`DROP TABLE TracksFts` (записываем для полноты, но в проде не используется).

**Почему `content='Tracks'`:** не дублируем данные, FTS хранит только индекс; `Tracks` остаётся single source of truth. `unicode61 remove_diacritics 2` — нормализация кириллицы/диакритики, чтобы «Цой» нашёлся по «цои».

### Edge-cases триггеров и почему именно так

**1. `content='Tracks'` + `content_rowid='Id'` (external content).**
Альтернатива — обычная (standalone) FTS-таблица, которая хранит копию данных. Минусы standalone: двойной объём, риск рассинхронизации, нужен `MERGE`-логика при upsert. Минус external content: если `Tracks` обновляется в обход триггеров (например, через `dotnet ef database update` raw-SQL или `BulkCopy`) — индекс уезжает. У нас все записи идут через EF Core → SQL стандартный `INSERT/UPDATE/DELETE`, триггеры срабатывают всегда. Зафиксировано как инвариант: «никаких raw-SQL модификаций `Tracks` в обход `LibraryDbContext`».

**2. Почему `'delete'`-команда в `Tracks_au` и `Tracks_ad`.**
External-content FTS-таблица не хранит данные сама — она хранит только обратные индексы. Чтобы удалить запись из индекса, нужно подать FTS старые значения колонок (он по ним вычислит, какие термы убрать). Если подать новые — индекс будет считать, что удаляет термы, которых там нет, и оставит мусор. Поэтому в `Tracks_au` и `Tracks_ad` идёт именно `old.*`.

**3. NULL-устойчивость.**
В нашей схеме `Album` и `Genre` могут быть пустой строкой, но не `NULL` (EF Core с `string` без `?` и `IsRequired()`/default '' это гарантирует). FTS5 спокойно индексирует пустые строки — ноль термов, нулевой оверхед. Защита от случайного `NULL` всё равно полезна: `COALESCE(new.Album, '')` в обоих триггерах — на случай, если в будущем кто-то поменяет схему на nullable и забудет обновить триггеры. Записываем так:
```sql
INSERT INTO TracksFts(rowid, Title, Artist, Album, Genre)
VALUES (new.Id,
        COALESCE(new.Title, ''),
        COALESCE(new.Artist, ''),
        COALESCE(new.Album, ''),
        COALESCE(new.Genre, ''));
```

**4. Update IsBuiltIn / DurationTicks / FilePath / CoverPath / AddedAtUtc.**
Эти колонки не индексируются FTS. `Tracks_au` срабатывает на UPDATE любой колонки (так работает SQLite — нельзя ограничить триггер списком колонок без `WHEN`-clause). Это значит: при обновлении только `CoverPath` мы зря дёргаем FTS (delete + insert). Решение — `WHEN`-clause:
```sql
CREATE TRIGGER Tracks_au AFTER UPDATE OF Title, Artist, Album, Genre ON Tracks
BEGIN
    ...
END;
```
`AFTER UPDATE OF <cols>` поддерживается SQLite и срабатывает только при изменении перечисленных колонок. Это снимает накладные расходы для частых non-FTS-апдейтов (в будущих итерациях, когда появятся `LastPlayedAt`, `Rating` и т.п.).

**5. Идемпотентность миграции.**
`CREATE VIRTUAL TABLE TracksFts USING fts5(...)` без `IF NOT EXISTS` упадёт, если кто-то накатил миграцию вручную, а потом EF попытался ещё раз. Защита: использовать `CREATE VIRTUAL TABLE IF NOT EXISTS TracksFts ...` (SQLite это поддерживает с 2017). То же для `CREATE TRIGGER IF NOT EXISTS`. Backfill (`INSERT INTO TracksFts(rowid, ...) SELECT ...`) идемпотентным не сделать дёшево, но он выполняется только в момент `Up()`, который EF не запускает повторно для уже применённой миграции — это даёт защиту на уровне `__EFMigrationsHistory`. Если кто-то очистил таблицу истории миграций руками — это уже мусор, не наш контракт.

**6. Конкурентность.**
SQLite в WAL-режиме (он у нас по умолчанию через `Microsoft.Data.Sqlite` 8+) разрешает одного писателя и многих читателей. Триггеры выполняются в той же транзакции, что и INSERT/UPDATE/DELETE, → атомарно с точки зрения других читателей. Если в момент `Append` истории прослушиваний параллельно идёт `Search` — FTS-чтение увидит либо состояние «до», либо «после», но не промежуточное. Это безопасно.

**7. Rebuild на случай повреждения индекса.**
Полезный admin-инструмент на будущее: `INSERT INTO TracksFts(TracksFts) VALUES('rebuild');` — пересоберёт индекс из `Tracks`. В 1.0.2 не выносим в UI, но фиксируем в `architecture.md` как «команда для починки руками через DB Browser, если кто-то пожалуется на странные результаты поиска». Полноценный «Rebuild search index» в меню — кандидат на 1.0.3+ или `1.4.0`/`1.9.0`.

**8. Размер таблицы и vacuum.**
External-content FTS даёт оверхед ~30–60% от размера индексируемых полей. На библиотеке 50k треков (средние строки ~50 байт × 4 поля) это +6–10 МБ. Не проблема. После массового импорта/удаления имеет смысл `INSERT INTO TracksFts(TracksFts) VALUES('optimize');` — но это тоже admin-команда, не в UI.

    content='Tracks',
    content_rowid='Id',
    tokenize = "unicode61 remove_diacritics 2"

            old.Id,

            COALESCE(old.Artist, ''),
            COALESCE(old.Album,  ''),
            COALESCE(old.Genre,  ''));

## Парсер пользовательской строки (FtsQueryBuilder)

Пользователь вводит свободный текст. Мы НЕ отдаём его сырым в `MATCH` (там есть зарезервированные операторы: `"`, `*`, `:`, `AND`, `OR`, `NOT`, `(`, `)`). Алгоритм:

1. Trim, split по whitespace.
2. Каждое слово: убрать кавычки/скобки/двоеточия (заменить пробелами); если осталось пусто — выбросить.
3. Каждое непустое слово обернуть в двойные кавычки и приписать `*` для prefix-match: `"цой"* "звезда"*`.
4. Склеить через пробел (неявный AND в FTS5).
5. Пустая итоговая строка → метод возвращает «нет результатов», презентация не вызывает SQL вовсе (или возвращает первые N из репозитория).

Это даёт «как ожидает пользователь» поведение и неуязвимо к инъекциям FTS-синтаксиса.

### Task 11 — Уточнение «недавнего» виджета

## Сознательные ограничения этой итерации

- **Без album-view и без группировки.** Поле `Album` появляется, но его UI-репрезентация — итерация D.
- **Без подсветки совпадений в результатах.** Это полировка UX, отдельная мини-задача в 1.0.x при наличии времени, не критична для DoD.
- **Без «search-as-you-type» в истории.** Поиск фильтрует только основной список треков.
- **Без CSV/JSON-экспорта статистики.** Экспорт планируется в `1.5.0` (Stats + Scrobbling).
- **Без аналитики «когда я слушал X в последний раз»** в карточке трека. Это легко доделать поверх `GetRecentUnique`, но входит в `1.5.0` дашборд.
- **`MainViewModel._allTracks` остаётся in-memory копией всей библиотеки.** На 50k треков это приемлемо (десятки МБ), на 500k уже нет. Замена на пагинацию + виртуализацию `ListBox` — кандидат на итерацию D или E, где альбомный view всё равно меняет паттерн загрузки. FTS-поиск в этой итерации **не** упирается в `_allTracks` — он идёт прямым SQL.
- **Application-слой остаётся слоем абстракций, не use-case-слоем.** `MainViewModel` — толстый оркестратор (Play/Add/Delete/Import/Save через прямые вызовы инфраструктурных интерфейсов). Переезд в `ImportTrackUseCase` / `DeleteTrackUseCase` / pipeline-handler-ы — отдельная итерация, ориентир `1.9.0` Architecture hardening (CommunityToolkit.Mvvm + MediatR-style). Если толщина `MainViewModel` начнёт мешать раньше — заводим мини-итерацию между B и H, явным diff'ом к роадмапу.
- **`ILibraryQueryService` как объединяющий фасад не вводим.** Поиск, история и навигация по библиотеке разнесены по узким интерфейсам (`ISearchService`, `IListeningHistoryRepository`, `ITrackRepository`). Объединение в один сервис — стилистическое предпочтение, его можно сделать в `1.9.0`, если контракты к тому времени стабилизируются и общий фасад начнёт приносить пользу.
